## 3. 灌演示数据（第一次真正碰 Milvus 与 BGE）

```bash

```

- [ ] 结束后打印出 **`★ 演示用户 user_id = ...`** —— 抄下来，第 4 步要用

- [ ] 再跑**第二遍**，输出**完全一样**、且**没有**"已下架 / 清理 / 对账"字样 ——
      这就是幂等的验收方式：同一个 doc_id 的 chunk_id 稳定，
      Milvus 里不会堆重复向量，两边也不会漂移

> **为什么文档是一篇多块，而不是一篇一块**
> chunk 是**检索与引用的单位**。整篇一块的话，无论问哪一半都会把整篇塞进证据，
> "逐句核对引用"也就失去意义 —— 引用指向一大段无关文字。
> 15 篇分成 84 块之后，引用能指到具体那一段。

**如果这一步报错，八成是这几处：**

| 报错 | 原因 | 处理 |
|---|---|---|
| Milvus sparse 字段类型错 / `data type not match` | `lexical_weights` 的键被当成了字符串 | 把 `app/services/encoder.py` 里 `{str(k): float(w) ...}` 改成 `{int(k): float(w) ...}` |
| 建集合报 dim 不匹配 | 换了嵌入模型（BGE-M3 dense 是 1024 维） | 同步改 `milvus_store.DENSE_DIM` |
| `The type of expr must be string, but NoneType is given` | 给 `MilvusClient.delete` 传了 `expr=`，而 pymilvus 2.4 的参数叫 **`filter`** | 别改回去：多出来的关键字会被 `**kwargs` 静默吞掉，只在"真的有条目要删"时才炸 |

### 6b. ⭐ 真实 HTTP 冒烟（服务必须真的起着）

```bash
# 终端 A
python -m app.api --host 127.0.0.1 --port 8090
# 终端 B
python scripts/smoke_api_live.py --base http://127.0.0.1:8090   # 57 项（脚本自己用 demo 账号登录，不需要 --user）
```

> 演示用户的 user_id 现在是**固定的** `22222222-2222-2222-2222-222222222222`。
> 以前每次跑 `seed_kb.py` 都会新建一个用户（`app_user` 主键带 `gen_random_uuid()`，
> 所以 `ON CONFLICT DO NOTHING` 永远不会命中），而演示预约的主键是固定的、
> `DO UPDATE` 里又没更新 `user_id` —— 于是预约一直绑在最早那个用户上，
> 换上新打印的 user_id 反而查不到预约，表现为改约场景莫名降级。
> 现在固定 UUID，`seed_kb.py` 可以随便重复跑。

> ⚠️ **跑 `smoke_api_live.py` 之前必须先跑一次 `python scripts/seed_kb.py`。**
> 改约场景会**真的把演示预约改掉**（它是端到端验收，不是只读探针），
> 所以连跑第二遍时会因为"预约已经不是原来那个状态"而失败 4 项。
> 这 4 项失败**看着像代码坏了，其实只是数据被上一遍消耗掉了** ——
> 先重跑 `seed_kb.py` 再判断，别急着改代码。

**为什么它和 `smoke_api.py` 不是重复的**：`smoke_api.py` 走 `httpx.ASGITransport`，
请求在**同一个进程内**直接交给 ASGI 应用，不经过 uvicorn 的启动流程、不经过网络。
实测它至少漏掉三类问题，全都是"服务根本不可用"级别的：

| 漏掉的问题 | 现象 | 为什么进程内测试看不到 |
|---|---|---|
| uvicorn 事件循环 | `python -m app.api` **启动即失败**（psycopg 不能在 ProactorEventLoop 上跑） | 它压根不经过 uvicorn |
| 坐席 id 类型 | 运营后台「接单」在真实库上 **100% 失败** | fake 是内存字典，非 UUID 字符串照收 |
| 时间戳类型 | 同上，「关单」也失败 | fake 对 ISO 字符串照收 |

- [ ] `GET /api/health` 返回 `profile=real`、`checkpointer=postgres`
- [ ] SSE 的所有 `status` 文案都来自 `STAGE_TEXT` 固定话术表（正文没混进过程通道）
- [ ] 篡改 `plan_hash` 后流程走完，但**绝不执行**
- [ ] 坐席接单后，聊天接口回的是 **`human_takeover` 回执而不是 AI 正文**（`final` 不出现）；
      关单后恢复正常作答。★ 注意**不是 409** —— 接管期间用户仍然可以说话
- [ ] 接管期间发的话**已落库**（`GET /api/sessions/{id}` 能看到），坐席端也看得到
- [ ] `GET /ops/panel` 是页面、`GET /ops/stream?once=true` 首帧是 `snapshot`
- [ ] 未知角色返回 403

> ⚠️ **`python -m app.api` 在 Windows 上的一个坑**（已修，但换机器/升级 uvicorn 后要留意）：
> uvicorn 把 Windows 的默认事件循环**硬编码**成 `ProactorEventLoop`，而 psycopg 的异步
> 连接只认 `SelectorEventLoop`。更绕的是 uvicorn 对 `loop="auto"` 和 `loop="asyncio"`
> **都**返回 Proactor，所以在 `__main__.py` 里 `set_event_loop_policy()` 完全没用
> （循环是在策略生效之前就建好的）。解决办法是给 uvicorn 传一个自定义循环工厂：
> `loop="app.api.loop:selector_loop_factory"`。详见 `app/api/loop.py` 的注释。

### 6d. 多轮对话案例集（`scripts/multi_turn_cases.py`）

上面那条记忆项要手打，容易漏。所以把**跨轮次才会暴露**的行为收成了一组可跑的案例：

```bash
python scripts/multi_turn_cases.py --list      # 只列案例，不花钱
python scripts/multi_turn_cases.py --case M2   # 跑一个
python scripts/multi_turn_cases.py --all       # 全跑（约 10–15 分钟，真实模型）
```

| 案例 | 逐轮输入 | 期望 | 守的是什么 |
|---|---|---|---|
| **M1** 指代消解 | ①热玛吉和超声炮有什么区别？ ②那个更适合我？ | 第 2 轮**接上**上一轮的项目，不反问"您说的是哪个" | 历史有没有进 `classify` |
| **M2** 非槽位事实 | ①我对利多卡因过敏 ②那我做热玛吉要注意什么？ | 第 2 轮回答里**出现"过敏"**，且不编造"不影响" | 回答类 Prompt 里有没有历史 |
| **M3** 槽位覆盖 | ①我做的是水光 ②不对，我做的是超声炮 ③我做的什么项目？ | 第 3 轮答的是**超声炮** | 槽位"可沿用、可被本轮覆盖"；★ 第 3 轮还会撞上"越界路径"（见下） |
| **M4** 澄清预算 | ①那个怎么样 ②那个怎么样 ③那个怎么样 | 前两轮追问；**第 3 轮不再追问**，且因为一句有用信息都没有 → **转人工** | `clarify_count` 是跨轮预算（上限 2），不能被每轮清零 |
| **M5** 转人工 | ①急症自述 → 坐席接单 → ②补充"还发烧" → 坐席回复 → 坐席关单 → ③那我需要注意什么？ | ①转人工 ②**200 + 接管回执、无 AI 正文**、已落库 ③AI 恢复作答**且记得"发烧"** | 接管不挡人 + 不抢话 + 跨接管边界的记忆 |
| **M6** 会话隔离（负例） | 会话 A：我对利多卡因过敏；会话 B：我有什么需要注意的吗？ | B 的回答里**不该**出现"利多卡因" | 记忆必须按 session 隔离 |
| **M7** 第三人称（观察项） | ①我朋友做的热玛吉，她需要注意什么？ ②那我做的什么项目？ | 只记录实际行为，**不判定** | 多人称是槽位抽取的经典难点 |

> ★ 挑案例的原则：**专挑没有退路的那条路径。**
> 测"记忆"要用**装不进槽位的事实**（过敏史、既往史）。用"我做的是水光"是测不出来的 ——
> `project` 槽位会替历史兜住，看起来一切正常。这一点本身比案例更值得记住：
> **验证一个能力时，要挑它最没有退路的那条路径。**
>
> 单轮冒烟测不出这些：每句话开一个新会话，"跨轮"的机制全部退化 ——
> 没有可以指代的对象、槽位沿用不到下一轮、`clarify_count` 永远停在 0。

#### 跑这组案例真的抓到过东西

第一遍跑就暴露了三个问题，其中两个是真缺陷：

| 现象 | 根因 | 怎么处理 |
|---|---|---|
| **M1** 第 2 轮走了 `handoff` + `error`，顾客只问了句"那个更适合我？"却收到"已为您转接人工" | 日志里是 `specialist_draft 结构化输出两次均不合格：citations.0 Input should be an object input_value='E1'` —— 模型把**上一轮回答里的 `[E1]`** 抄进了本轮 citations | 这是**给回答类 Prompt 注入历史之后引入的**：历史里带着 `[E1]` 标记。修法是两条一起上：① `HISTORY_RULES` 明说历史里的引用编号不属于本轮；② `SpecialistDraftOut` 容忍裸字符串（那里的 citations 不是溯源凭据），而 `KbDraftOut` 保持严格（那里的 citations **就是**凭据） |
| **M3** 第 3 轮回了"这个问题建议由顾问或医生为您解答，我这边先不做判断" | 节点路径是 `classify → dispatch → kb_intake → kb_return`：越界判定后**直接跳到收口**，没有任何草稿，于是吐固定话术。而 `project=超声炮` 就在槽位里 | 越界路径上加了 `kb_ctx_reply`：先用已有的槽位与历史试答一次，答不了再照旧转交。硬约束是"**空内容 = 什么都不做**"，锁在 `smoke.py` 的 `ctx_reply_patch` 上 |
| **M5** 第 3 轮回答里没出现"发烧"三个字 | 其实**记对了**（症状槽位里写着"…、发烧"，回答也说"您描述的情况…建议尽快就医"），是**我的断言写错了** | 断言改成"接管期间那句话进了会话上下文"+"回答没把这件事当没发生"。**测"有没有记住"要看上下文有没有带上，不是看它复述不复述** |
| **M5** 换了一轮跑，第 3 轮变成 `hard_rules → block → audit_block`：**顾客什么都没收到，工单也没有** | 硬性规则 MED-002「给出用药建议」的模式里有 `涂抹`，而顾客发烧+眼睛看不清时，正确的话恰恰是"**不要**自行涂抹任何外用产品" —— 最安全的方向被判成"在给用药建议"。改三轮后按"重复命中升级为 block"变成阻断 | 给字面匹配加**否定语境**判定（与紧急词表当初修"热玛吉"里的"热"是同一类坑）。放宽之后仍要拦住真的用药建议，所以否定词用词组、还要检查否定是否被后面的"请/建议/可以"推翻 |

**还留着一个未修的问题（等确认）**：上面那条的**后果**比误报本身更值得注意 ——
一轮内容被硬性阻断时，用户拿到的是"本次内容被硬性阻断"，**没有答案、也没有工单**。
对隐私类阻断（"把手机号发我"）这样处理没问题；但这一轮是顾客术后发烧+视力异常在问
"要注意什么"，**什么都不给、也没人跟进**，正好撞上项目自己那条原则
"宁可多转一次人工，也不要让用户对着空气说话"。
可能的改法：内容被 block 且 `handoff_ticket` 为空时，**兜底建一张 P1 工单**（和
"图执行异常兜底转人工"同一个取向）。这属于改 `blocked` 的语义，先不动，记在这里。

## 已知的、这份清单无法覆盖的事项

1. **规则资产未经审定**：`app/config/rules.yaml` 里的紧急词表与高风险标签是草稿 v0.1，
   必须经**医学顾问与法务**过一遍才能上线。自测只能验证"规则是否按预期生效"，
   验证不了"规则本身对不对"。
2. **独立复核缺口**：单模型下 `escalation` 与首次审查同族，不构成独立复核（已在审计里标注）。
   要真正解决，得填 `ESCALATION_MODEL` 接另一家模型 —— 那时图代码一行不改。
3. **视觉链路未实现**：图片只入库不解析，转人工时明确告知，不假装看图。
4. **知识库内容是演示稿，未经医学/法务审定**：15 篇 / 84 chunk 是按公开常识写的演示材料，
   上线前必须由医学顾问**逐条**审。自测只能验"能不能被检索到、引用是否指向具体块、
   项目过滤有没有误伤通用资料"，**验不了"内容对不对"**。
5. **`MIN_RERANK=0.30` 对 bge-reranker-v2-m3 偏严（已量测，未擅自调整）**：
   `check_retrieval.py` 的 15 条验收里，**5 条最高分落在 0.149–0.299，而最高分全部来自
   正确的 chunk** —— 即检索找对了、证据闸门把它扔了，`kb_evidence` 于是一条都不留，
   回答降级成"资料不足 + 建议面诊"。对客最明显的是"皮秒做完会不会反黑"（0.183，
   而该块字面就含"反黑"）与"怎么确认医生有没有资质"（0.299）。
   **安全相关的三条已稳在阈值之上**（眼睛发黑 0.931 / 术后发烧更肿 0.927 / 伤口化脓 0.306）。
   ⚠️ 改这个阈值等于改**安全闸门**，属产品决策，需要确认后再动。备选：
   (a) 降到 0.15；(b) 改成"最高分附近取若干条 + 绝对下限"的相对筛选；(c) 维持现状接受降级。
6. **口语→书面语的词面鸿沟（已量测并部分缓解）**：精排对"顾客怎么说"与"资料怎么写"
   之间的用词差异很敏感。同一句"做完脸肿得厉害还发烧是不是感染了"：
   对含该内容的**完整清单**只打 **0.0091**，对其中"发热伴局部红肿"六个字打 **0.2254**，
   无关对照 **0.0039** —— 模型没问题，是词面对不上，且长清单会**稀释**分数。
   缓解办法是在安全关键条目里加"顾客常问：…"的口语问句引导（**不改动医学结论原文**），
   实测把安全关键用例从 0.039 拉到 0.927。
   ⚠️ 这是**词面层的缓解，不是根治**；根治要在检索侧做查询归一化，
   否则每来一种新说法都得再补一次词面。另需注意：写引导时**不能照抄验收问句**，
   否则就成了"拿写进去的句子考自己"——`check_retrieval.py` 的问句是故意换个说法的。

第 25–28 条有共同的形状：**都在"看起来能用"和"其实语义错了"之间**。
25 是两套出口字段不一致（手动刷新就好了）、26 是事件驱动冒充状态同步、
27 是职责边界随状态变化而失效、28 是探针本身有副作用。
四条里有三条的修法都是同一句话：**把判断依据收敛到唯一来源**。

第 21、22 条的共同点是**"单测全绿、整体不对"**：接口各自都符合自己的契约，
但把它们连起来看，用户体验是坏的。前者要两端并排走一遍才看得见，
后者要挑一个**装不进槽位**的事实才能试出来 —— 用"我做的是水光"是试不出来的
（`project` 槽位会替它兜住），这一点本身就值得记住：
**验证一个能力时，要挑它最没有退路的那条路径。**

第 23、24 条来自"用户自己测出来的 bug"，教训各是一句话：

- **同一个状态有多个副本，就一定会有一条路径漏掉其中一个。**
  接管状态散在四处（`takeover` / `lastSeenTaken` / 提示条 `hidden` / placeholder），
  而 `newChat()` 只写了前两个 —— 修法不是"记得在 newChat 里也补一遍"，
  而是把它收敛成**只有一个写入口**（`syncTakeover`），其余路径一律调它。
- **给一个 Prompt 加新内容，等于给所有引用它的契约加了一个新输入。**
  历史里带着上一轮回答的 `[E1]` 标记，而另一个字段的 schema 恰好只认对象 ——
  两个互不相干的东西就这样撞在一起。而报错信息（`citations.0 Input should be an object`）
  与用户看到的现象（"已为您转接人工客服"）看起来毫无关系，
  中间隔着"结构化输出失败两次 → LLMError → 兜底转人工"三层。
  这也是**把服务端异常记进日志**（第 19、20 条的修复）第一次真正派上用场的地方：
  没有那条 `logger.exception`，这次只能靠猜。

第 17、18 条是一对，教训很具体：**"文件里有这行语句"不等于"它被执行了"。**
第 18 条尤其反直觉 —— 我明明在文件里写了补列语句，跑完列还是不在，
因为一条更早的 `CREATE INDEX` 已经让脚本中断了。而且它只在**升级旧库**这条路上出现：
新建库时列和索引一起建，顺序无所谓，所以本地怎么测都是绿的。

现在这条路径由 `python scripts/check_schema.py` 守着：在临时库里把新列删掉模拟旧库，
再跑一遍 schema.sql，验证列补上了、历史行回填成 DEFAULT 而不是 NULL、索引建回来了。
（写完之后特意把那个 `CREATE INDEX` 挪回去验证过一次 —— 这个检查确实会红，
不是个永远绿的摆设。）

第 19、20 条其实是**同一个拼写错误**造成的两个现象。它值得单独记一笔，
因为它暴露的是**错误处理的设计问题**，而不只是笔误：

```js
// 改之前：一个大 try 包住"校验令牌 + 全部初始化"
try {
  const r = await fetch("/ops/auth/me", ...);
  if (!r.ok) { 清掉令牌; 弹登录页; return; }   // ← 任何非 200 都算"没登录"
  await bootData();                          // ← 里面任何一个 bug 也冒到这里
} catch (e) { 弹登录页("无法连接服务"); }      // ← 连"为什么"都不打印
```

三个后果叠在一起，把一次普通的函数名写错包装成了"登录失效"：

1. **`!r.ok` 就删令牌** —— 后端 500、网络抖动，都算"请你重新登录"；
2. **一个大 try 包住初始化** —— 界面渲染的 bug 被归因到认证上；
3. **catch 里不留原始异常** —— 屏幕上只有"无法连接服务"，控制台里什么都没有。

改法是拆成一条明确约定：**只有 401 / 403 才算"没登录"**，其余情况一律
保留令牌并如实报错；初始化每一步各自兜异常，互不连累。

教训：**错误处理里"归错因"比"没处理"更贵。** 没有兜底时异常会直接冒到
控制台，一眼就能看到 `connectStream is not defined`；而"贴心的"兜底把它
翻译成了用户看得懂、开发者却完全被带偏的一句话。

同时补上 `check_ui.cjs` 的 **F 组**：A~E 全是静态文本扫描，抓不到这种东西 ——
语法没错、DOM id 都在、被调的函数名也在别处定义过（只是不叫这个）。
只有给一个最小 DOM 桩 + 假 fetch，把脚本在"已登录、正在刷新"的状态下
**真的跑一遍**才能发现。F 组还会手动触发一次轮询定时器，
断言坐席回复确实被画进了对话区、且不会重复追加。
（同样验证过它会红：把 `connect` 改回 `connectStream`，F 组立刻报
"没请求过 `/ops/stream`" + `ReferenceError: connectStream is not defined`。）

第 16 条尤其值得记住：**算指标之前先搞清"哪些行不该算进来"。**
27 条备注行把升级率从 25% 抬到 43%，而我据此得出的"93% 的升级是浪费的"也跟着错了
（真实是 85%）。结论方向没错，但数字错了 —— 拿错数字去推动优化，比没有数字更危险。

两条结论，建议带进真实档位的自测：

- **fake 档位证明的是"接线对"，不是"功能对"。** 它做得越省事（忽略参数、恒返回成功、
  恒返回 verified、对任何类型照收），就越会以"帮你测过了"的方式骗你。
  第 4、5、10、11 条都是这样漏过去的 —— 它们的共同形状是"**fake 比真实世界宽容**"。
- **报错信息本身要当验收项。** 第 4 条如果直接说"缺少 appointment_id"，
  五分钟就能定位；说成"状态已变化"，会让排查方向整个偏到并发冲突上。
  一个误导性的报错，比一个直接的报错贵得多。

第 10、11 条还留下一条更普遍的教训：**同一个概念在两张表里用了不同类型**
（`ops.handoff_event.actor` 是 TEXT，`assigned_to` 却是 UUID）。这种"同概念不同型"
本身就是坏味道，看到时应当直接统一，而不是去迁就它。判断标准写在
`sql/schema.sql` 末尾的「类型约定」里：**系统自己生成的 id 用 UUID，
外部系统给定的 id 用 TEXT**。
