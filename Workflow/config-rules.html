规则资产与参数基线（MVP v0.1）

使用说明
本文是可执行的配置草稿，不是最终合规文本。落地时应当：

  1. 词表与标签清单必须经医学顾问与法务审定后才能上线；
  2. 全部内容以数据表形式落库（见 data-model.md 的 rule_registry / emergency_lexicon），
    而不是硬编码在代码里 —— 规则要能热更新、能版本回滚、能进审计；
  3. 每次修改都产生新版本号，审计记录里保留命中的规则编号与版本。

MVP 阶段知识库内容可以暂缓，但规则资产不能暂缓 —— 它是风险审查子图的判定依据。

1.4 P2 标签（关注，不升级）

效果不满意、担心、焦虑、反复追问同一问题（>4 次）、询问其他机构、比价、要求看案例。

1.5 判定规则（这一节比词表更重要）

只做关键词匹配会大量误报。必须带上下面四条规则：

#规则命中不命中
1第一人称 + 现在时/近期自述才算症状"我现在眼睛看不清"、"昨天做完今天脸发白"——
2询问风险 ≠ 出现症状——"热玛吉会导致失明吗？"、"网上说会失明"、"会不会烂脸" → 走普通科普路径
3否定不算——"我没有视力模糊"、"不疼了"
4第三人称 / 假设不算——"我朋友做完眼睛看不清"（可打 P2 + 建议其就医）、"如果失明了怎么办"

共现要求：泛词（疼 / 肿 / 红 / 麻）不能单独触发，必须与部位或程度或时间共现：

  • "有点疼" → 不触发
  • "疼得受不了" → P1
  • "填充的地方发白，还特别疼" → P0（部位 + 颜色异常 + 剧烈疼痛三要素）

时间窗只用于降噪，不作为排除依据：术后 30 天内的 P1 症状可升级；P0 不看时间。

实现建议：规则层用 Aho-Corasick 多模匹配 + 正则（处理否定与疑问句式）+ 共现窗口；
模型（emergency_triage）只做规则未命中时的兜底，且只回答"是否升级"，
不做任何医学判断。

1.6 误报回流

运营面板必须提供"标记误报"按钮（见 ops-console.md）。被标记的样本进入调优队列，
每条记录携带：原始消息、命中的规则编号与版本、坐席判断。
没有这条回流，词表永远调不准。

2.2 升级（escalate）触发组合

命中任一 HIGH 标签                    → escalate
命中 ≥ 2 个 MEDIUM 标签               → escalate
三位专家对同一句判定不一致             → escalate（意见冲突）
最低 confidence < 0.6                 → escalate（模型自报不确定）

escalate 后由 escalation 角色复核；最终等级仍由决策表给，模型只提供证据与建议。

3.2 block 与 revise 的边界

判据一句话：改文案也解决不了 → block；改文案能解决 → revise。

  • AD-001 到 MED-003 属于"话说得越界"，改写即可合规 → revise
  • PRIV / OPS / LEG 属于"这件事本身不能做" → block，且 block 不产生任何业务出站内容

3.3 重复命中升级规则

同一 rule_id 在复审中重复命中 → 升级为 block。

理由：说明生成侧对这条边界的理解是错的，继续退回改写只会浪费预算并可能换个说法再犯。
实现：hard_rule_hits 里按 rule_id 聚合，命中次数 ≥ 2 且跨轮次 → 直接 block。

4. 澄清策略

4.1 什么时候追问

只有"缺失信息会实质影响回答"时才追问，一般性科普不追问。

用户问追问吗原因
"热玛吉和超声炮有什么区别？"否一般科普，直接讲原理/流程/恢复期差异
"我适合做哪个？"是答案取决于部位、恢复期、既往史
"这个多少钱？"是缺项目名，价格无法查询
"术后能运动吗？"看情况缺项目与术后天数；若用户已在本会话说过项目，则不追问

4.2 追问模板库（按缺失类型，都是封闭式）

缺失类型模板
缺项目名"想先确认您说的是哪个项目？可以告诉我是热玛吉 / 超声炮 / 水光针中的哪一个，或直接说项目名称。"
缺部位"您主要想改善的是面部紧致、下颌轮廓，还是其他部位？"
缺恢复期偏好"您更希望当天可正常上班，还是可以接受 3–7 天的轻微红肿？"
缺既往史"以前做过同类项目吗（如热玛吉 / 超声炮 / 线雕）？"
缺术后天数"方便告诉我是术后第几天吗？不同阶段的护理建议不一样。"
缺门店"您想咨询的是浦东店还是静安店？"
完全无法定位（超预算兜底）不再追问，直接给一般性说明 + 建议面诊，或转人工

模板设计要求：一次最多 2–3 问、给选项、不引导答案、不带诊断性质、结尾必带面诊提示。

4.3 上限与兜底

MAX_CLARIFY = 2（连续追问两次不收敛即兜底）。完整规则见 langgraph-pseudocode.md §3.4。

6. 规则版本化与生效约定

  1. 编号格式：类别-序号，如 AD-001、PRIV-002、OPS-003。编号一旦发布不复用、不改含义。
  2. 版本号：v<主>.<次>，主版本表示判定逻辑变化，次版本表示增删词条。
  3. 每次命中都记录：rule_id + version + 命中位置（原文片段）+ 命中时间 → 写进 review_audit.hard_rule_hits。
  4. 回归测试集：每改一次词表或规则，跑一遍固定的误报/漏报样本集（至少覆盖 §1.5 的四条判定规则）。
  5. 生效方式：MVP 阶段用数据库表 + 应用内缓存（60 秒刷新）；不做需要重启的配置。

这套约定看着"重"，但它正是面试里能体现工程成熟度的地方：
规则可追溯、可回滚、可评测，而不是散落在代码里的 if-else。
